# API Contract

## Global Context Envelope

Every public business API must use a standard envelope.

Both request and response use the same top-level JSON key:

```text
context
```

This keeps the API contract simple and consistent:

```text
request:  context + data
response: context + data
```

Health checks and internal infrastructure endpoints can be exceptions:

```text
GET /actuator/health
GET /actuator/info
```

## HTTP Method Policy

Public business APIs use `POST` so every request can carry the full `context` body.

This applies to reads and lists too:

```text
POST /api/v1/account/list
POST /api/v1/card/list
POST /api/v1/transfers/recent/list
```

Reason:

```text
GET request bodies are not consistently supported by clients, proxies, gateways, and tooling.
```

Infrastructure endpoints can still use `GET`.

Internal service APIs should also prefer `POST` when they need a context envelope, validation metadata, idempotency, or a structured request body.

## Request Envelope

Standard shape:

```json
{
  "context": {
    "requestId": "018f4a6a-8f22-7c5c-b3af-5d91c7e0c111",
    "account": {
      "accountNumber": "123456789012345678",
      "profileId": "prf_123"
    },
    "os": {
      "name": "Android",
      "version": "15"
    },
    "app": {
      "version": "1.0.0",
      "buildNumber": "100",
      "isRooted": false,
      "language": "en-US",
      "theme": "dark"
    },
    "device": {
      "deviceId": "dev_123",

`data` contains the endpoint-specific request body.

    "username": "user1",

```

## Request Context Fields

### requestId

Purpose:

```text
trace one request across gateway, services, logs, and responses
```

Rules:

- Client should send it.
- API Gateway must generate it if missing.
- Every service must log it.
- Every response must return the same request ID.
- Prefer UUID/ULID format.

### account

Fields:

```text
accountNumber
profileId
```

Purpose:

```text
selected account and active profile context for the request
```

Rules:

- Can be null during registration, login, and onboarding.
- `accountNumber` must be exactly 18 numeric digits when present.
- Must be validated against JWT user identity.
- Must be validated against account-service ownership data.
- Must not be trusted just because the client sent it.

### os

Fields:

```text
name
version
```

Examples:

```text
Android 15
iOS 18
Web
```

Purpose:

```text
analytics, risk checks, debugging, compatibility decisions
```

### app

Fields:

```text
version
buildNumber
isRooted
language
theme
```

Purpose:

```text
client compatibility, risk checks, localization, UI preference support
```

Security note:

```text
isRooted is a client-provided signal. Treat it as risk information, not as a trusted fact.
```

### device

Fields:

```text
deviceId
model
fingerprint
```

Purpose:

```text
device verification, login risk checks, fraud detection, audit
```

Rules:

- Device ID must match a verified device before high-risk operations.
- Fingerprint should not expose raw sensitive hardware identifiers.
- Device verification status is owned by `iam-service`.

### network

Fields:

```text
ipAddress
connectionType
operator
```

Purpose:

```text
risk checks, audit, fraud detection, troubleshooting
```

Security note:

```text
server-derived IP address from gateway/load balancer is more trustworthy than client-reported IP address.
```

## Response Envelope

Standard shape:

```json
{
  "context": {
    "requestId": "018f4a6a-8f22-7c5c-b3af-5d91c7e0c111",
    "correlationId": "support-req-123",
    "profileId": "prf_123",
    "status": {
      "code": "SUCCESS",
      "message": "Success",
      "httpStatus": 200,
      "details": []
    }
  },
  "data": {}
}
```

`data` contains the endpoint-specific response body.

## Response Context Fields

### requestId

Must be the same request ID received in request `context` or generated by the gateway.

### correlationId

Support identifier normalized by the API Gateway from `X-Correlation-Id`.

Rules:

- Present in controlled error responses.
- Can be null on older success responses until all controllers include it.
- Must be safe for logs: letters, digits, `-`, `_`, `.`, and `:` only.
- Must not replace the request ID, trace ID, or span ID.

### profileId

The active profile ID used by the service for this response.

Rules:

- Can be null for register, login before profile creation, and infrastructure endpoints.
- Must match the validated profile when the request is profile-scoped.

### status

Fields:

```text
code
message
httpStatus
details
```

Rules:

- `code` must use the `StatusCode` enum.
- `message` is a clear human-readable message.
- `httpStatus` is the HTTP status number.
- `details` is optional but should be an empty list when there are no details.
- There is no separate `error` object.

## StatusCode Enum

All API responses must use one of these values:

```text
SUCCESS
CREATED
ACCEPTED
VALIDATION_ERROR
UNAUTHORIZED
FORBIDDEN
NOT_FOUND
CONFLICT
DUPLICATE_REQUEST
BUSINESS_RULE_VIOLATION
INSUFFICIENT_FUNDS
LIMIT_EXCEEDED
FEATURE_DISABLED
DEVICE_VERIFICATION_REQUIRED
ACCOUNT_REQUIRED
KYC_REQUIRED
KYC_PENDING
EXTERNAL_SERVICE_ERROR
SERVICE_UNAVAILABLE
INTERNAL_ERROR
```

Use business-specific state fields inside `data` when the state is part of a successful business response.

Example:

```json
{
  "context": {
    "requestId": "018f4a6a-8f22-7c5c-b3af-5d91c7e0c111",
    "profileId": "prf_123",
    "status": {
      "code": "SUCCESS",
      "message": "Success",
      "httpStatus": 200,
      "details": []
    }
  },
  "data": {
    "accountCompletionStatus": "KYC_REQUIRED"
  }
}
```

## Validation Failure Response

Validation failures are represented only through `context.status`.

There is no separate `error` object.

```json
{
  "context": {
    "requestId": "018f4a6a-8f22-7c5c-b3af-5d91c7e0c111",
    "profileId": "prf_123",
    "status": {
      "code": "VALIDATION_ERROR",
      "message": "Invalid request",
      "httpStatus": 400,
      "details": [
        {
          "field": "data.amount",
          "message": "must be greater than zero"
        }
      ]
    }
  },
  "data": null
}
```

## Unauthorized Response

Missing, invalid, malformed, expired, or untrusted tokens return `401`.

```json
{
  "context": {
    "requestId": "018f4a6a-8f22-7c5c-b3af-5d91c7e0c111",
    "profileId": null,
    "status": {
      "code": "UNAUTHORIZED",
      "message": "Unauthorized",
      "httpStatus": 401,
      "details": []
    }
  },
  "data": null
}
```

## Java DTO Direction

The JSON field is always `context`, but Java can still use different DTO types for request and response if that keeps validation clear.

Shared envelope/value DTOs should live in the narrow `contract` module defined in [API Fields](./api-fields.md). Service-specific request and response DTOs stay inside the owning service.

Suggested model:

```text
ApiRequest<T>
ApiResponse<T>
RequestContext
ResponseContext
Status
StatusCode
AccountContext
OsContext
AppContext
DeviceContext
NetworkContext
StatusDetail
```

Implementation rule:

```text
controllers receive ApiRequest<SpecificRequest>
controllers return ApiResponse<SpecificResponse>
```

Example:

```text
ApiRequest<LoginRequest>
ApiResponse<LoginResponse>
```

## Validation Rules

Every service must validate:

- `context` is present.
- `context.requestId` is present or generated by gateway.
- `data` is valid for that endpoint.
- `context.account.profileId` belongs to authenticated user when required.
- `context.account.accountNumber` belongs to `context.account.profileId` when required.
- Device is verified when the operation is sensitive.

## Trust Rules

Never fully trust client-provided context.

Trusted sources:

```text
JWT claims after signature validation
gateway-generated request ID
server-derived IP address
service database ownership checks
verified device record from iam-service
```

Client-provided context is useful for:

```text
debugging
analytics
risk scoring
localization
client compatibility
```

Client-provided context is not enough for:

```text
authorization
account ownership
profile ownership
device verification
financial operation permission
```
