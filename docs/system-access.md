# System Access

This document defines access rules for public APIs, user-token APIs, admin/internal APIs, service-to-service APIs, and safe develop/debug access.

It also defines how developers can generate test tokens and bypass selected flows safely without weakening production security.

For environment profiles, variables, and deployment rules, see [Environments](./environments.md).

## Access Levels

| Level | Meaning | Token Required | Used For |
| --- | --- | --- | --- |
| `PUBLIC` | Client can call without user token. | No | Login, register, key exchange, public job list. |
| `ONBOARDING` | User is known but onboarding is not complete. | Limited user token | Device verification, referral during registration, account registration. |
| `USER` | Normal authenticated customer access. | User JWT | Account, card, PFM, transfer, KYC status. |
| `ADMIN` | Privileged operator/admin access. | Admin JWT | Feature flag update, KYC approval, card unblock/expire. |
| `INTERNAL_SERVICE` | Service-to-service access. | Service credential | Ledger internal APIs and protected internal service calls. |
| `ENVIRONMENT` | Infrastructure access. | Environment-dependent | Actuator health/info endpoints. |
| `DEBUG_ONLY` | Develop-only testing access. | Debug guard required | Token generation, mock OTP, fake scenarios. |

## Enforcement Model

The API Gateway is the public security boundary.

Gateway responsibilities:

- Validate JWT signature, issuer, audience, expiration, and token type.
- Reject missing, invalid, malformed, or expired user tokens with `401 Unauthorized`.
- Reject authenticated users without permission with `403 Forbidden`.
- Strip all inbound identity headers from external clients.
- Add trusted internal identity headers only after validation.
- Strip `X-Internal-Service-Token` from every public request.
- Own app-level request decryption if enabled.
- Route public, user, admin, and internal requests correctly.

Trusted headers added after successful JWT validation:

```text
X-Authenticated-User-Id
X-Authenticated-Profile-Id
X-Authenticated-Device-Id
X-Authenticated-Token-Id
X-Authenticated-Roles
X-Authenticated-Scopes
```

These headers are internal hints only. Services continue to validate the
forwarded bearer token and enforce ownership/business authorization.

Service responsibilities:

- Re-check ownership and business authorization.
- Never trust client-provided `context` alone.
- Never trust external identity headers unless they were produced by the gateway.
- Validate user/profile/account ownership against service data.
- Validate service-to-service requests on internal endpoints.

## Token Types

### User Access Token

Used by normal customer APIs.

Rules:

- Short lived.
- No refresh token.
- Expired token requires login again.
- Contains minimum required claims only.
- Must include user identity.
- May include active profile, device, roles, and scopes.

### Limited Onboarding Token

Used during onboarding before the user is fully active.

Rules:

- Shorter lifetime than normal user token.
- Limited scopes only.
- Allows only onboarding APIs.
- Should not allow transfer, card, PFM, or sensitive account operations.

Suggested scopes:

```text
ONBOARDING_ACCOUNT_REGISTER
ONBOARDING_DEVICE_VERIFY
ONBOARDING_REFERRAL_SET
ONBOARDING_PHONE_SET
ONBOARDING_IAM_REGISTER
```

### Anonymous Onboarding Token

A special limited onboarding token issued by `POST /api/v1/iam/login` with
`reason=REGISTER`, before any user exists.

Rules:

- Short TTL (default 15 minutes, `REDBANK_JWT_ANONYMOUS_TOKEN_TTL_SECONDS`).
- Subject is a synthetic onboarding-session UUID, not a user ID.
- Role is `ONBOARDING`.
- Scopes are exactly `ONBOARDING_PHONE_SET`, `ONBOARDING_DEVICE_VERIFY`,
  and `ONBOARDING_IAM_REGISTER`.
- Must not grant access to any account, card, PFM, or transfer API;
  the gateway returns `403 Forbidden` for those routes.
- The login route is rate-limited more strictly at the gateway because these
  tokens are minted without credentials.

### Admin Token

Used by operators or admin tools.

Rules:

- Must include admin role/scope.
- Must be issued through a trusted admin authentication flow.
- Must be audited.
- Must not be generated by normal user login.

### Service Token

Used for service-to-service calls.

Rules:

- Not exposed to clients.
- Used only inside private service network.
- Should include service name and allowed scopes.
- Later production option: mTLS plus signed service token.

## Develop Debug Access

Debug access must make development faster without creating production danger.

The rule is:

```text
debug tools are real code paths with fake authority, isolated to develop only
```

Debug tools must never be enabled in production.

## Debug Safety Requirements

All debug endpoints and mock behavior must follow these rules:

- Available only in `develop` profile.
- Disabled by default unless explicitly enabled.
- Controlled by a clear property such as `redbank.debug.enabled=true`.
- Application must fail startup if debug is enabled in `prod`.
- Debug endpoints must live under `/debug/v1/**`.
- Debug endpoints must not be routed by production gateway.
- Debug tokens must be short lived.
- Debug token issuer must be clearly different from production issuer.
- Debug tokens must use develop-only signing keys.
- Debug actions must be logged.
- Debug actions should include request ID and developer identifier when available.
- Debug endpoints must never access real production data.

Suggested Spring Boot guards:

```text
@Profile("develop")
@ConditionalOnProperty(name = "redbank.debug.enabled", havingValue = "true")
```

Production startup guard:

```text
if profile is prod and redbank.debug.enabled is true, fail application startup
```

## Debug Token Generation

### POST /debug/v1/tokens/user

Purpose:

```text
generate short-lived user access token for develop testing
```

Access:

```text
DEBUG_ONLY
```

Rules:

- Only available in develop.
- Disabled unless `redbank.debug.enabled=true`.
- Uses develop-only signing key.
- Token lifetime should be short, such as 15 minutes.
- Token must contain obvious debug issuer, such as `red-bank-debug`.
- Should allow selecting existing develop user ID and profile ID.
- Should not create production-compatible tokens.
- Should be logged as a debug token generation event.

Suggested token claims:

```text
iss = red-bank-debug
aud = red-bank-api
sub = user id
profile_id = profile id
device_id = debug-device
scope = requested scopes
roles = USER
exp = now + 15 minutes
```

### POST /debug/v1/tokens/admin

Purpose:

```text
generate short-lived admin token for develop admin API testing
```

Access:

```text
DEBUG_ONLY
```

Rules:

- Only available in develop.
- Should require an additional debug secret or localhost/develop-network binding.
- Uses develop-only signing key.
- Token lifetime should be very short, such as 10 minutes.
- Should log admin token generation loudly.
- Must never exist in production runtime.

### POST /debug/v1/tokens/service

Purpose:

```text
generate short-lived service token for develop service-to-service testing
```

Access:

```text
DEBUG_ONLY
```

Rules:

- Only available in develop.
- Must specify service name.
- Must specify allowed scopes.
- Should be used for internal ledger and service-to-service tests.
- Token lifetime should be short.

## Debug OTP Behavior

### Mock Device OTP

For develop testing, device verification can accept:

```text
111111
```

Rules:

- Only allowed when `redbank.debug.mock-otp.enabled=true`.
- Only available in develop.
- Must never work in production.
- Must not be stored as a real OTP.
- Must not bypass audit logging.
- Logs should say mock OTP path was used.
- Response behavior should match normal successful verification.

Suggested property:

```text
redbank.debug.mock-otp.enabled=true
```

Production guard:

```text
if profile is prod and redbank.debug.mock-otp.enabled is true, fail application startup
```

## Debug Flow Examples

### Fast User API Testing

Use this flow when account/user records already exist in the develop database:

```text
1. Call POST /debug/v1/tokens/user
2. Copy token into Postman Authorization header
3. Call user API through api-gateway
4. Service validates token using normal JWT validation path
```

Important:

```text
debug token still goes through the normal authentication filter
```

This keeps debug behavior close to real behavior.

### Fast Device Verification Testing

Use this flow when testing device verification in develop:

```text
1. Enable redbank.debug.mock-otp.enabled=true
2. Start iam-service in develop profile
3. Call POST /api/v1/iam/device-verify with OTP 111111
4. IAM marks device as verified using normal success flow
```

Important:

```text
mock OTP replaces only the code comparison, not the whole device verification use case
```

The service should still validate user, device, challenge purpose, status transition, and audit logging.

### Fast Admin API Testing

Use this flow for admin-only APIs:

```text
1. Call POST /debug/v1/tokens/admin
2. Use token for admin API
3. Gateway validates admin role/scope
4. Service validates admin role/scope again where needed
```

Admin debug tokens must not be used in shared or production-like environments unless explicitly approved for that environment.

## What Not To Do

Never do these:

- Do not add a production endpoint that accepts arbitrary user ID and returns token.
- Do not accept `111111` OTP in production.
- Do not skip authorization filters in local tests.
- Do not use production JWT signing keys for debug tokens.
- Do not put debug endpoints under `/api/v1/**`.
- Do not hide debug behavior inside normal production services without profile/property guards.
- Do not rely only on frontend environment to hide debug flows.

## Recommended Implementation Shape

Recommended package/module structure:

```text
api-gateway
  debug
    DebugTokenController
    DebugTokenService
    DebugAccessProperties
    DebugStartupGuard

iam-service
  debug
    MockOtpProperties
    DebugStartupGuard
```

Recommended configuration:

```yaml
redbank:
  debug:
    enabled: false
    mock-otp:
      enabled: false
```

Develop override:

```yaml
spring:
  profiles:
    active: develop

redbank:
  debug:
    enabled: true
    mock-otp:
      enabled: true
```

Production rule:

```text
prod profile must force all debug properties to false
```

## Testing Requirements

Add automated tests for debug safety:

- App fails to start when debug token endpoint is enabled in prod.
- App fails to start when mock OTP is enabled in prod.
- Debug token endpoint is unavailable when debug is disabled.
- Mock OTP `111111` is rejected when mock OTP is disabled.
- Mock OTP `111111` is rejected in prod profile.
- Debug token uses debug issuer, not production issuer.
- Normal JWT validation accepts debug token only in develop.

## Audit Requirements

Audit these debug actions:

- Debug user token generated.
- Debug admin token generated.
- Debug service token generated.
- Mock OTP used.

Audit fields:

```text
request_id
developer identifier if available
environment
debug action
target user/profile/service
issued scopes
expiration time
timestamp
```
